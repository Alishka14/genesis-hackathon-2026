# LedgerGym: состояние разработки

20.11.2026 капитан сообщил, что в команде три участника, и поручил начать разработку. Имена/аккаунты остальных участников и конкретные ревьюеры ещё не указаны. Четыре функциональные области можно распределить между тремя людьми после согласования команды. Это разрешение на разработку не разрешает merge, изменение доступа, публичную публикацию или отправку.

Основа: main `f5c37776911b11b592229ab6d93e7e415597415a`, draft PR #1 `a70316253408e9e1521a79199ba6b33e718d63de`; последний содержит планы, не конкурсный код. Подготовлены черновой интерфейсный контракт, план и первый локальный код.

Первичные PDF общего положения и FinTech-кейса в текущем сеансе не предоставлены. Утверждения об официальных условиях в репозитории и спецификации — вторичные источники и требуют проверки по первоисточникам. Особенно важны поля, сумма каждого типа ошибки, допуск и дополнительные evidence.

Прототип **не готов к конкурсной оценке**: тестовая финансовая история мала и условна; полноценных четырёх типов ошибок, двух compound, hard negatives, 20 эпизодов и baseline-набора нет. У процесса агента и оценщика нет внешней границы изоляции; in-process callback, объект среды, filesystem и Python не защищают truth от недоверенного кода. Среда годится только для доверенных локальных экспериментов. Закрытую оценку нельзя заявлять безопасной. Метод полноценного доказательства повторного обязательства и финансовая полнота требуют дополнительного review.

## Результаты проверок первого среза

В локальном окружении Python 3.12 и pytest 8.4.2: `python -m pytest -q` — 14 passed; `python -m ledgergym` — один синтетический пример, TP=1, FP=0, FN=0, F1=1, reward=0.996 после двух исследовательских шагов. Это результат smoke test с собственной тестовой политикой на собственной игрушечной истории, не benchmark, не подтверждение полноты модели и не оценка независимого агента.

## Замечания к документам

- План с четырьмя ролями не означает четыре человека: капитан подтвердил три участника; назначения и ревью пока не указаны.
- В старом тексте `SCOPE.md` роль ожидалась и код блокировался; дополнение документа фиксирует последующее прямое разрешение капитана начать P0. Это не подтверждение уже распределённых задач между людьми.
- Правила extra evidence, точное определение суммы для каждого fault, финансовые допуски, отдельная доставка reward в closed mode и трактовка последнего шага не окончательно согласованы. В `INTERFACES.md` предложения помечены как предварительные.
- Равенство полей двух синтетических счетов само по себе не доказывает идентичность обязательства в реальном учёте. Нужна явная публичная бизнес-идентичность и адекватные hard negatives до полноценного генератора.
- Доступность официальных документов и фактические конкурсные критерии нужно проверить по первоисточникам; существующее описание регламента в PR #1 само по себе не заменяет документы.
