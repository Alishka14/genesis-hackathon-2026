# LedgerGym — тренажёр финансового аудита для ИИ-агентов

LedgerGym генерирует синтетическую бухгалтерию компании с заранее внедрёнными ошибками и даёт агенту найти их через ограниченный набор инструментов, как аудитору. Агент не видит эталона. Его находки оцениваются по доказательствам, а не по угаданным ID.

- **Что внутри эпизода:** главная книга (200–2000 проводок), счета, платежи и курсы валют (20–200 документов), учётная политика и 0–12 ошибок четырёх типов.
- **Что делает агент:** листает таблицы, открывает документы, считает на калькуляторе и отправляет находки. На всё у него 100 шагов и ограничение по времени.
- **Что получает:** F1 по найденным ошибкам и награду со штрафом за лишние шаги. Ложные обвинения и «отметить всё подряд» наказываются.

Python 3.11+, только стандартная библиотека, без сети и внешних API. Лицензия MIT.

## Быстрый старт

```bash
git clone https://github.com/Alishka14/genesis-hackathon-2026.git
cd genesis-hackathon-2026
```

Веб-панель на демо-данных (создаёт 10+10 эпизодов во временной папке):

```bash
python3 -m ledgergym.dashboard --demo
```

Открыть http://127.0.0.1:8765. В панели: обзор эпизодов, сравнение политик, просмотр публичных таблиц, найденные расхождения с доказательствами и пошаговый **Agent Replay**. Остановить — Ctrl+C.

Полный набор 10 train + 10 dev с прогоном четырёх базовых политик и проверкой повтора всех траекторий (папка должна быть новой):

```bash
python3 -m ledgergym.company_dataset "$HOME/ledgergym-run" --evaluate --settlement-hard-negatives
```

Диагностика агентов (P, R, F1, возврат, шаги, время и разбор сбоев по типам) на этом наборе и на 30 новых эпизодах с невиданными seed и параметрами:

```bash
python3 -m ledgergym.agent_diagnostics --dataset "$HOME/ledgergym-run" --held-out 30
```

## Как это устроено

```
генератор компании ──► эпизод: public/ (агенту)  +  private/ (только оценщику)
                                   │
                    агент в Docker ◄┤ reset / step: 5 действий, 100 шагов, тайм-аут
                                   │
                       оценщик ◄───┘ submit → сопоставление 1:1 → F1, награда
```

**Генератор** (`ledgergym/company_world.py`, `company_world_v2.py`) строит согласованную историю начислений и платежей, проверяет финансовые инварианты и только потом внедряет ошибки:

| Тип ошибки | Пример |
| --- | --- |
| `duplicate_invoice` | один и тот же счёт проведён дважды |
| `payment_allocation` | платёж разнесён не на тот счёт |
| `fx_rate_or_date` | неверный курс или дата курса валюты |
| `reporting_period` | операция попала не в тот отчётный период |

Есть два связанных сценария (`fx_allocation`, `duplicate_allocation`), чистые эпизоды без ошибок и правдоподобные «ловушки»: частичные оплаты, возвраты, платёж одним переводом по нескольким счетам. Эти ловушки ошибками не являются.

**Действия агента:** `list_records` (постранично, с курсором), `get_record`, `get_document`, `calculator`, `submit`. Канонический формат — `{"name": ..., "args": {...}}`. Плоская форма `{"action": ..., ...}` и `submit` с `{"episode_id", "findings"}` прямо в args тоже принимаются и оцениваются одинаково.

**Оценка** (`ledgergym/score.py`): находка засчитывается, если совпадают тип, затронутые записи, сумма и валюта, а приведённые доказательства содержат хотя бы один допустимый полный набор. Находки сопоставляются с ошибками строго один к одному (максимальное паросочетание).

```
награда = clip(2 · F1 − 1 − 0.002 · шаги_проверки, −1, 1)
```

Нормализация, допуск и выбор при неоднозначности (весь код в `ledgergym/score.py`):

- **Допуск по сумме — 0 минимальных единиц** (`AMOUNT_TOLERANCE_MINOR = 0`): все суммы целые, эталон считается по опубликованному правилу округления (`policy.json` → `rounding`, `ROUND_HALF_EVEN`).
- `affected_ids` сравниваются как множество (порядок и повторы не важны) и должны точно совпасть с эталоном. `evidence_ids` должны существовать в публичных данных и покрывать хотя бы один допустимый набор; лишние существующие ID не штрафуются. Тип и валюта сравниваются точно, текст `explanation` на оценку не влияет.
- **Неоднозначность:** сначала берётся максимально возможное число совпадений, затем ошибки перебираются по `issue_id`, и каждой достаётся находка с наименьшим индексом, которая не уменьшает итоговое число совпадений. На TP, FP, FN и награду этот выбор не влияет.
- Повторная находка той же ошибки — FP. Неверная структура `submit` (больше 30 находок, больше 10 ID доказательств, объяснение длиннее 1000 символов, чужой `episode_id`, лишние поля) завершает эпизод с наградой −1.

**Конфигурация генератора** для `generate_episode(seed, config, output_dir)` и `reset(seed, {"mode": "train", "team_config": config})`: `postings` (200–2000), `documents` (20–200), `faults` (число ошибок каждого из 4 типов), `compounds` (`fx_allocation`, `duplicate_allocation`), а также переключатели вариативности `fault_parameters: "varied"`, `timestamp_offsets: "mixed"` и `evidence_alternatives: true`. Пустой config даёт чистую компанию. Пример: `{"postings": 800, "documents": 100, "faults": {"reporting_period": 1}, "compounds": {"fx_allocation": 1}}`. Версии записаны в каждом эпизоде: `schema_version` в `manifest.json`, `accounting_model` в `policy.json`, `generator_version` и полный config в закрытом `provenance.json`.

**Изоляция** (`ledgergym/isolated_runner.py`): агент запускается в Docker-образе, закреплённом по digest, без сети, с read-only файловой системой, от непривилегированного пользователя и с лимитами ресурсов. В контейнер монтируется только скрипт агента, эталон остаётся у оценщика.

**Точки входа для жюри** (`judge_adapter.py`): `generate_episode(seed, config, output_dir)`, `make_env()` и `score_episode(episode_dir, findings, inspection_steps)`. Контракт описан в [docs/INTERFACES.md](docs/INTERFACES.md).

## Результаты

Четыре базовые политики из §06 кейса, измерено `ledgergym.agent_diagnostics`. P и R микроусреднены по всем находкам; F1, возврат, шаги и время — средние на эпизод; время зависит от железа.

**Открытый набор 10 train + 10 dev** (20 эпизодов, из них 4 чистых, 42 ошибки):

| Политика | P | R | F1 | Возврат | Шаги | Время, с | Ложные обвинения на чистых | Пропущено по типам |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| oracle (знает эталон, только для контроля) | 1.00 | 1.00 | 1.00 | 1.000 | 0 | 0.001 | 0/4 | 0 из 42 |
| reconciliation (сверка по правилам) | 1.00 | 1.00 | 1.00 | 0.952 | 23.8 | 0.045 | 0/4 | 0 из 42 |
| seeded random | 0.00 | 0.00 | 0.00 | −1.000 | 23.8 | 0.028 | 4/4 | 42 из 42 |
| mark-all (отметить всё) | 0.00 | 0.00 | 0.00 | −1.000 | 23.8 | 0.028 | 4/4 | 42 из 42 |

**30 новых эпизодов** с seed и сочетаниями параметров, которых нет в открытом наборе (300–2000 проводок, режим `varied`, смешанные часовые пояса, альтернативные наборы доказательств; 5 чистых, 145 ошибок): oracle и reconciliation — P = R = F1 = 1.00, возврат 1.000 и 0.956, ложных обвинений на чистых нет; random и mark-all — F1 = 0, возврат −1, ложные обвинения на всех 5 чистых.

**Разбор сбоев.** Random и mark-all не получают ни одного TP: их находки ссылаются на счёт целиком вместо затронутых записей и не содержат полного набора доказательств, поэтому каждая из них — FP. Mark-all при этом подаёт по 4 находки на каждый счёт (600 FP на открытом наборе), и награда упирается в нижнюю границу −1. Reconciliation теряет только штраф за шаги (≈24 шага × 0.002), oracle шагов не тратит.

Тесты из §05 кейса закреплены в автотестах: полный верный ответ лучше молчания на ошибочных книгах, молчание лучше ложных обвинений на чистых, дубли не дают выгоды, «пометить всё» даёт −1, а экономия шагов лишь немного различает равные ответы.

**Воспроизводимость и инвариантность.** Все 60 траекторий повторяются шаг в шаг с тем же счётом. Перестановка строк во всех таблицах вместе с биективной заменой всех ID на другой формат (`INV/2026/000123`, hex, `r7`, юникод) сохраняет ответ и награду oracle: 40 из 40 вариантов на 5 конфигурациях, через `JudgeEnv` и через `score_episode`. После отката записанных в `provenance.json` изменений книги сходятся (дебет = кредит по каждой валюте, суммы счетов и платежей сходятся), а все доказательства достижимы через инструменты: 40 эпизодов, 280 ошибок, 0 нарушений. Эталон точно воспроизводится по публичным записям независимым модулем `ledgergym/independent_audit.py`, который не использует код генератора и сверки: 75 из 75 ошибок на 20 эпизодах симуляции жюри.

## Ограничения

- **Сверка по правилам решает все эпизоды** (F1 = 1.0), простые стратегии получают 0. Сверку писали те же авторы, что и генератор, поэтому её результат подтверждает согласованность данных и оценщика, а не трудность задачи для модели. Прогона LLM-агента нет, обучения весов нет (по кейсу оно необязательно).
- **Разнообразие ограничено:** 4 типа ошибок, валюты KZT/USD. Режим с варьированием сумм, валют и часовых поясов есть (`--varied`), но в опубликованный набор не включён.
- **Все данные синтетические.** Модель упрощена: нет налогов и курсовых разниц между начислением и оплатой.
- **Результаты локальные** и не являются оценкой на закрытых тестах организаторов. Docker-изоляция проверена тестами, но независимого аудита безопасности не было.
- Встроенный в панель checker работает по правилам и не является обученной моделью.

## ИИ и открытый код

Проект создан командой с активным использованием ИИ-ассистентов. Это раскрыто по §08 положения хакатона:

- **OpenAI Codex:** основной код генератора, среды, оценщика, изоляции, офлайн-сборки и тестов.
- **ChatGPT:** проработка архитектуры, исследовательские модули EQT/FAA/CAB и документация.
- **Claude Code (Anthropic):** аудит перед сдачей, опциональный режим генератора `--varied`, воспроизводимая матрица финансовой проверки, оформление лицензии, исправления, проверочные прогоны и этот README.

Подробная разбивка: [docs/PROVENANCE_AND_AI_DISCLOSURE.md](docs/PROVENANCE_AND_AI_DISCLOSURE.md).

Код в рантайме использует только стандартную библиотеку Python; чужой исходный код не копировался. Для тестов и сборки используются pytest, setuptools и wheel; их версии и хэши закреплены в lock-файлах. Собственный код распространяется по лицензии MIT ([LICENSE](LICENSE)).
