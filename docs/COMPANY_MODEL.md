# Модель масштабируемой компании — lg-014

Проектные правила по мастер-спецификации; оригинальный FinTech PDF ещё не сверен. Этот документ фиксирует реализацию для review, не официальный финансовый стандарт.

## Конфигурация

`scenario="company"`, `postings` — целое 200–2000, `documents` — целое 20–200. Документы — invoices + payments; FX и manifest не считаются первичными документами. Две проводки начального финансирования и минимум две на каждый документ означают `postings >= 2*documents+2`. Дополнительные проводки возникают из оплачиваемых компонентов услуг, а не копирования строк. Допускается нечётное количество проводок: у счёта несколько дебетовых строк и одна итоговая кредитовая.

`faults` задаёт количество каждого из четырёх типов; `compounds` — количество `fx_allocation` и `duplicate_allocation`. По умолчанию оба словаря пусты. Сумма одиночных ошибок плюс удвоенное число compound ограничена 12. Невозможные сочетания числа документов, валютных операций и ошибок отклоняются до генерации. Переключатели не меняют исходную чистую историю при неизменных seed/размерах.

## Учёт

Одна компания, февраль 2026, рабочее смещение +05:00, базовая валюта KZT, документы KZT/USD (по два знака). Синтетические поставщики оказывают услуги; уникальная бизнес-ссылка service_ref находится в строках счёта. Разные законные услуги могут иметь одинаковую сумму и дату у одного поставщика.

Счёт начисляет расход (дебет expense по компонентам услуги) и кредит payable. Политика: округление общей суммы в KZT HALF_EVEN, округление компонентов с остатком на последнем компоненте. Платёж в день выставления счёта гасит часть payable и кредитует bank. Для текущей модели нет переноса платежа на другую FX-дату, курсовых разниц между датой начисления и оплаты, налогов, возвратов и кредит-нот. Начальный взнос капитала финансирует платежи; расходование денег не создаёт непредусмотренный овердрафт.

Публичные расширения: manifest.company_id; ledger.line_id/reporting_period/rate_id; invoice line_items.line_id/service_ref; payment.remittance_invoice_id; публичные policy. ID случайны, не кодируют тип ошибки. Порядок таблиц перемешан. Курс выбирается по дате операции в +05:00, не по текстовому UTC-префиксу; расписание содержит предыдущую дату для проверяемых ошибочных конвертаций.

## Ошибки и доказательства

- Duplicate: у двух проведённых счетов одна business identity (поставщик, service_ref) вместо двух законных услуг. Сумма — один лишний счёт в валюте документа; affected — оба invoice_id; evidence — оба документа и их итоговые строки payable.
- Allocation: сумма платежа недораспределена относительно явного remittance_invoice_id либо направлена другому счёту того же поставщика/валюты. Сумма — недостающая целевому счёту сумма в KZT по правильному курсу; affected — целевой invoice_id и payment_id. Доказательства: целевой документ, платёж, его проводки, документ другого назначения при наличии, правильный FX rate при USD.
- FX: обе платёжные проводки используют предыдущий дневной курс, сохраняя баланс. Сумма — абсолютное расхождение с правильной конвертацией в KZT (0 допустим, если неверная дата дала тот же округлённый результат); affected — payment_id и дебетовая строка; evidence — invoice/payment docs, обе проводки, правильный FX rate.
- Period: все строки одного счёта отнесены к предыдущему месяцу вопреки рабочему timezone. Сумма — сумма счёта в KZT; affected — invoice_id; evidence — документ и итоговая строка payable. Такая область affected отличается от двухстрочной учебной фикстуры и явно задаётся этим контрактом.

Compound FX/allocation связывает две ошибки одного частичного платежа: сумма allocation в KZT зависит от правильного FX, а не от ошибочной бухгалтерской оценки. Compound duplicate/allocation направляет платёж на дублирующий счёт; обе проверки используют общие документы. Расхождения разных типов не складываются в общий ущерб.

Каждый evidence set содержит не более 10 публичных IDs; число findings не превышает 12. Истина создаётся из внедрений, затем проверяется отдельно по публичным фактам. Проверяющий модуль применяет точную рациональную арифметику для независимой проверки Decimal-округления генератора. Сверочный baseline использует публичный проверяющий модуль и потому не является независимым benchmark.

## Файлы и воспроизводимость

`build_company` возвращает public/truth/provenance; export требует private provenance с соответствующим seed. Все изменения полей отражены в закрытом журнале; применение их в обратном порядке восстанавливает чистую историю. Версия генератора — company-0.1. Decimal-контекст создаётся явно и не зависит от точности/ловушек вызывающего кода; расписание FX формируется из целых сотых.

`company_dataset --evaluate` создаёт 10 train и 10 dev эпизодов. В каждом split есть чистые контроли, все четыре отдельных типа, оба compound и смешанный пример из 12 ошибок. Размеры и наборы ошибок перемешиваются отдельно для каждого split. По структурным ограничениям смешанный случай требует не меньше 40 документов. Набор открытый, небольшой и построен по известным правилам; он не измеряет обобщение на независимых финансовых данных.
