# Два разных сопоставления в LedgerGym

Дата: 21.11.2026. Реализован ограниченный первый этап §5 плана v2. Публичные файлы, Sandbox API и reward не меняются. Этот документ фиксирует исполняемые правила внутреннего модуля; он не утверждает нечитанный оригинальный FinTech PDF.

## 1. Payment–Invoice Matching

`ledgergym.payment_matching.allocate_payments(invoices, payments)` — чистая доверенная функция: входы не изменяются. Она проверяет распределение денег по **явным документальным ссылкам**, не классифицирует нарушения и не получает hidden truth.

Внутренний invoice содержит `invoice_id`, `entity_id`, `currency`, `issued_at`, `total_minor`; опциональный status — `issued` (по умолчанию в текущей модели) или `cancelled`. Внутренний payment содержит `payment_id`, `entity_id`, `currency`, `timestamp`, `amount_minor`, `invoice_refs=[{invoice_id,amount_minor}]`; kind поддерживает только `payment`. Дополнительные поля исходных документов не используются. Все ID непустые, без внешних пробелов; денежные поля — настоящие int, не bool/float. Invoice total >0, payment amount >=0, каждая reference amount >0. Timestamp требует offset. Валюты — три заглавные ASCII-буквы; арифметика ведётся отдельно в каждой валюте.

`entity_id` платежа — внутренний вход. В существующем `payments.jsonl` его нет: адаптер `validate_clean_company_allocations(public)` получает его из согласованного payment journal **до внедрения ошибок**, а не из заявленной invoice reference. Новый публичный столбец не добавляется. Отсутствующие или противоречащие друг другу entity в журнале отклоняются.

### Семантика результата

`payments[payment_id]` содержит status, currency, allocations, unallocated_minor, candidate_ids, errors. Подтверждённое распределение содержит invoice_id, amount_minor, basis=`explicit_invoice_ref`. `invoice_balances[invoice_id]` содержит currency, paid_minor, outstanding_minor.

| Статус | Значение |
| --- | --- |
| ALLOCATED | Вся сумма платежа распределена; сам invoice может быть оплачен лишь частично |
| PARTIAL | Часть платежа применена по явным ссылкам, оставшаяся сумма сохранена отдельно |
| UNALLOCATED | Ничего не применено; отсутствие ссылки не заменяется совпадением суммы, даже если кандидат один |
| AMBIGUOUS | Без ссылок есть несколько допустимых кандидатов либо одновременно заявленные ссылки конкурируют за недостаточный остаток; подтверждённых распределений нет |
| INVALID | Ссылка неизвестна/дублирована, контрагент/статус/дата неверны, превышена доступная сумма; весь платёж оставлен нераспределённым |
| UNSUPPORTED | Явная ссылка требует конвертации между разными валютами; FX-policy распределения ещё не реализована |

Ошибочная структура, отрицательная сумма, refund/reversal kind, неизвестный invoice status вызывают ValueError до расчёта. Ошибки деловых связей дают структурированный результат. Ни один статус сам по себе не становится truth issue или агентским finding.

### Порядок и сохранение денег

1. Проверить все записи и уникальность invoice/payment ID, не позволять словарю скрыть дубликат.
2. Обрабатывать платежи по фактическому UTC-времени. Эквивалентные timestamp с разными offset входят в одну группу.
3. Проверить все ссылки платежа относительно остатков **до группы**. Нет существования, контрагента, действующего статуса, допустимой даты или суммы — не применять ни одну часть split payment. Неверную ссылку не заменять эвристикой.
4. Для допустимых платежей группы сложить спрос по каждому invoice. Если спрос превышает его остаток, все платежи, затрагивающие этот invoice, получают AMBIGUOUS целиком. Другие платежи группы продолжают выполняться. Повторной жадной попытки выбрать «лучшего» после исключения конкурентов нет.
5. Применить только неконфликтующие явные суммы. Излишек платежа не списывать, не округлять и не переводить на другой счёт автоматически.

Для каждого поддерживаемого платежа: `sum(allocations)+unallocated_minor==amount_minor`; для каждого invoice: `paid_minor+outstanding_minor==total_minor` и `0<=paid_minor<=total_minor`. Outstanding — арифметически неприменённая часть номинала документа; для cancelled invoice это не утверждение о наличии долга: он исключён из кандидатов и недоступен для оплаты. Суммы разных валют не складываются в общий денежный итог.

ID используются лишь для стабильной сериализации. Переименование ID и перестановка строк не определяют победителя при конкуренции. Порядок по времени разрешён только для подтверждённых явных ссылок; он не используется как основание для угадывания invoice без ссылки.

### Интеграция и ограничения

Генератор company вызывает дополнительную проверку после существующего clean preflight и до fault injection. Его текущая policy требует распределить весь платёж на remittance invoice; поэтому PARTIAL/UNALLOCATED/AMBIGUOUS/INVALID/UNSUPPORTED не проходят этот clean preflight. Законный частичный платёж по счёту проходит: его собственная сумма полностью распределена.

Общий модуль уже проверяет несколько платежей на invoice, split и свободный остаток, но **генератор company пока не создаёт эти новые ситуации**: его policy, journal и truth требуют отдельного расширения. Модуль не доказывает подлинность invoice_refs; например, семантически неверная ссылка на другой счёт того же контрагента может удовлетворять денежным ограничениям. Это проверяет `company_checks` по отдельной публичной модели/документальному намерению.

PAY-01–05 и PAY-08–12 покрыты в `tests/test_payment_matching.py`. PAY-06 (возврат) и PAY-07 (межвалютное распределение) остаются незавершёнными; проверен только честный отказ, а не поддержка. Нативные USD→USD и KZT→KZT поддерживаются независимо; это не FX allocation. Cross-date FX, возвраты, сторно, порядок отмен и документы изменения условий требуют отдельной финансовой семантики и review.

## 2. Ground Truth Matcher

Существующий `ledgergym.score.evaluate` сопоставляет **findings с hidden issues**, а не платежи со счетами. Ребро допускается при совпадении типа, множества affected IDs, точной суммы, валюты и наличии полного allowed evidence set; дополнительные evidence IDs должны существовать публично. Применяется максимальное 1:1 сопоставление; повторные findings становятся FP. Формулы P/R/F1 и `clip(2*F1-1-0.002*inspection_steps,-1,1)` прежние. Допуск 0 и обработка extras — предварительные решения из `INTERFACES.md`, ожидающие сверки по первоисточнику. Новый финансовый модуль в scorer не подключён.

## Уточнение evaluator matching, 21.11.2026

Все доверенные пути оценивания теперь используют единый `addressable_ids(public)`: уникальные record IDs внутри разрешённой таблицы и doc_id документов invoices/payments. Видимый foreign key entity_id, company_id, line_id или ссылка на отсутствующий invoice сам по себе не становится доступным доказательством. Для FX без rate_id сохраняется существующий составной ключ date:source_currency:target_currency. Неизвестные таблицы исключаются. Правило get_document с первым совпавшим doc_id не изменено; модуль не заменяет валидацию данных.

Среди всех максимальных matching выбирается лексикографически минимальный вектор индексов findings для issues, отсортированных по issue_id; unmatched идёт после всех индексов. Каждый выбор проверяет достижимость оставшейся максимальной мощности, поэтому tie-break не превращает алгоритм в greedy. При уникальных строковых issue_id перестановка truth не меняет назначение. Для отсутствующих/нестроковых/повторных issue_id fallback — исходный индекс; официальная схема такого fallback не утверждается. Assignment остаётся у оценщика, поля score/reward не расширяются.

Четыре конфликта правил нормализации перечислены в MATCHER_CONTRACT_DECISIONS.md. Публичные лимиты, invalid-submit и денежный допуск в этом этапе сохранены.
