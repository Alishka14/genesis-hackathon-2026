## 1. Executive Summary

В рамках финансового аудита LedgerGym проведена повторная проверка бухгалтерских сценариев, денежных величин ошибок, валютных пересчётов, отчётных периодов и составных аномалий (*compound faults*).

Основная цель аудита — установить, что синтетические бухгалтерские данные обладают проверяемыми финансовыми инвариантами, а заявленные суммы аномалий согласуются с публичными бухгалтерскими записями.

**Главный результат: 1500 из 1500 выполненных проверок завершились успешно, без зарегистрированных ошибок.**

Результат включает:

- 700 проверок бухгалтерских миров;
- 200 структурных проверок составных сценариев;
- 200 арифметических проверок составных сценариев;
- 400 проверок одиночных типов финансовых аномалий.

Всего проверено **700 уникальных комбинаций сценария и seed**. Остальные проверки повторно используют часть этих комбинаций для проверки других свойств.

**Важно:** 1500 проверок не означают 1500 независимых миров, 1500 денежных тестов или подтверждение фактического финансового ущерба.

## 2. Scope — область аудита

Аудит охватывает генератор `ledgergym.company_world.build_company()`, публичные бухгалтерские таблицы, разметку `truth["issues"]`, данные `provenance` и результаты публичного анализатора `ledgergym.company_checks.inspect_company()`.

Проверены семь конфигураций:

| Конфигурация | Назначение |
|---|---|
| `clean` | Мир без внедрённых ошибок |
| `duplicate_invoice` | Дублирование счёта |
| `payment_allocation` | Ошибка распределения платежа |
| `fx_rate_or_date` | Неверный валютный курс или дата |
| `reporting_period` | Неверный отчётный период |
| `fx_allocation` | Совместная ошибка FX и распределения платежа |
| `duplicate_allocation` | Совместная ошибка дублирования счёта и распределения платежа |

Для каждой конфигурации использованы seed от 0 до 99.

Аудит не включает проверку реальных банковских операций, внешнюю финансовую экспертизу или независимое подтверждение экономического ущерба.

## 3. Методология и воспроизводимость

### 3.1. Принцип проверки

Для каждого тестового сценария:

1. Создавался синтетический бухгалтерский мир с фиксированным seed.
2. Из публичных таблиц извлекались соответствующие документы, платежи, проводки и валютные курсы.
3. Вычислялись проверяемые финансовые величины или структурные инварианты.
4. Результаты сопоставлялись с ожидаемыми значениями и, где применимо, с выводами `inspect_company()`.
5. Регистрировались количество проверок, успешные результаты и исключения.

Массовые проверки были воспроизведены через PowerShell с запуском Python из корня проекта.

### 3.2. Уровень независимости

Часть денежных величин пересчитывалась отдельным проверочным кодом с использованием `Decimal` и `ROUND_HALF_EVEN`.

Публичный анализатор `inspect_company()` использует рациональную арифметику на основе `Fraction`, отличную от реализации арифметики генератора.

Однако совпадение результатов не является полностью независимой финансовой экспертизой: генератор, проверочные скрипты и анализатор опираются на общие правила предметной области.

### 3.3. Хранение доказательств

Проверки воспроизведены в текущей рабочей среде, их итоговый вывод зафиксирован в ходе аудита.

На момент подготовки отчёта отдельные постоянные test-run logs и самостоятельные тестовые скрипты для всех 1500 проверок в репозиторий ещё не добавлены.

Поэтому отчёт фиксирует **воспроизведённые результаты**, но не утверждает, что уже существует полностью автоматизированный CI-процесс для их повторения.

## 5. Бухгалтерский баланс — 700/700 PASS

### 5.1. Проверяемый инвариант

Для каждой бухгалтерской истории проверялось:

**Σ debit_minor = Σ credit_minor**

Выполнены проверки для шести типов аномальных сценариев по 100 seed, всего 600 миров.

Дополнительно проверены 100 чистых миров:

- общий дебет равен общему кредиту;
- список `truth["issues"]` пуст.

**Результат: 700/700 PASS, 0 FAIL.**

### 5.2. Интерпретация

Результат подтверждает сохранение глобального бухгалтерского баланса во всех проверенных конфигурациях.

При этом сбалансированные проводки не гарантируют отсутствие ошибок распределения платежей, валютных пересчётов или отчётных периодов.

Поэтому проверка баланса рассматривалась как базовый инвариант, а не как доказательство полной финансовой корректности.

## 6. Compound-сценарии — 400/400 PASS

### 6.1. Структурные проверки — 200/200

Проверены два типа составных ошибок:

- `fx_allocation`: 100 seed;
- `duplicate_allocation`: 100 seed.

Проверялось наличие связанных ошибок, корректность ссылок на платежи и документы, структура бухгалтерских проводок и сохранение баланса.

Для `fx_allocation` подтверждалась связь обеих ошибок с общим платежом.

Для `duplicate_allocation` проверялись типы ошибок, пересечение затронутых идентификаторов и несовпадение назначения платежа с фактическим распределением.

**Результат: 200/200 PASS.**

### 6.2. Арифметические проверки — 200/200

Для `fx_allocation` проверены:

- валютная разница между корректным и использованным курсами;
- величина нераспределённой части платежа после конвертации;
- совпадение обеих сумм с `truth` и `inspect_company()`;
- валюта KZT для обеих рассчитанных аномалий.

Для `duplicate_allocation` проверены:

- совпадение сумм дублирующихся счетов;
- связь счетов с одной услугой;
- корректность суммы платежа и распределения;
- соответствие величин обеих ошибок ожидаемым и обнаруженным суммам.

**Результат: 200/200 PASS.**

### 6.3. Риск двойного подсчёта

Составная ошибка может содержать несколько аномалий, относящихся к одному платежу, счёту или бухгалтерскому событию.

Поэтому суммы таких аномалий нельзя автоматически складывать и объявлять общей финансовой потерей.

`provenance["compound_groups"]` следует использовать для идентификации связанных ошибок и сохранения информации об их пересечении.

## 7. Аудит одиночных финансовых аномалий — 400/400 PASS

### 7.1. `payment_allocation` — 100/100

Для каждого seed определялась нераспределённая часть платежа:

`gap = payment.amount_minor − Σ invoice_refs.amount_minor`

Если валюта платежа отличалась от KZT, сумма конвертировалась по корректному курсу на локальную дату платежа.

Использовалось округление `ROUND_HALF_EVEN`.

Проверялось совпадение результата с:

- `truth["issues"][...]["expected_amount_minor"]`;
- `inspect_company(public)[...]["claimed_amount_minor"]`.

Также проверялись положительность разницы и валюта KZT.

**Результат: 100/100 PASS.**

### 7.2. `fx_rate_or_date` — 100/100

Для каждого seed находились:

- сумма платежа в USD;
- корректный курс на дату платежа в UTC+5;
- фактически использованный в проводках курс;
- две бухгалтерские проводки соответствующего платежа.

Валютная разница вычислялась как:

`abs(convert(payment, correct_rate) − convert(payment, recorded_rate))`

Конвертация выполнялась с использованием `Decimal` и `ROUND_HALF_EVEN`.

Проверялись несовпадение корректного и ошибочного `rate_id`, соответствие записанных сумм использованному курсу и согласованность с `truth` и `inspect_company()`.

**Результат: 100/100 PASS.**

### 7.3. `reporting_period` — 100/100

Для затронутого счёта находились бухгалтерские проводки, не связанные с платежами.

Правильный период определялся по временной метке проводки в часовом поясе UTC+5:

`YYYY-MM`

Проверялось, что все соответствующие проводки записаны в другом периоде, а валюта и заявленная сумма ошибки совпадают между `truth` и `inspect_company()`.

**Результат: 100/100 PASS.**

Показательный пример для `seed=42`:

| Показатель | Значение |
|---|---|
| Проводок по счёту | 5 |
| Проводок с неправильным периодом | 5 |
| Записанный период | `2026-01` |
| Правильный период | `2026-02` |

Этот тест не включал отдельный арифметический пересчёт суммы счёта.

### 7.4. `duplicate_invoice` — 100/100

Для каждого seed проверялись:

- наличие двух затронутых счетов;
- равенство их `total_minor`;
- совпадение валют;
- соответствие суммы дублирующегося счёта `expected_amount_minor`;
- совпадение суммы и валюты с `inspect_company()`.

**Результат: 100/100 PASS.**

Это подтверждает согласованность денежных величин в проверенных синтетических сценариях, но не устанавливает реальную сумму ущерба.

## 8. Financial Amount Semantics

В рамках документации LedgerGym зафиксировано различие между денежной величиной аномалии и фактическим финансовым убытком.

| Тип ошибки | Значение суммы |
|---|---|
| `duplicate_invoice` | Номинальная сумма дублирующегося счёта в валюте счёта |
| `payment_allocation` | Нераспределённая или ошибочно распределённая часть платежа, выраженная в KZT |
| `fx_rate_or_date` | Абсолютная разница между правильной и записанной суммой в KZT |
| `reporting_period` | Сумма счёта, отнесённого к неправильному периоду, выраженная в KZT |

Поля:

- `expected_amount_minor` — ожидаемая величина аномалии из разметки сценария;
- `claimed_amount_minor` — величина, заявленная публичным анализатором;
- `currency` — валюта соответствующей величины.

Эти поля не следует интерпретировать как подтверждённые финансовые потери.

Даже совпадающие суммы аномалий могут описывать разные экономические эффекты, а связанные compound-ошибки могут частично относиться к одному событию.

## 9. Financial Impact Aggregation — proposed design

В `docs/INTERFACES.md` подготовлен проект интерфейса:

`analyze_financial_impact(public, truth, provenance)`

Предполагаемый модуль: `ledgergym/financial_impact.py`.

Планируемые результаты включают:

- `issue_count` — число обнаруженных аномалий;
- `anomalies` — список аномалий с их суммами и валютами;
- `overlap_groups` — группы связанных ошибок;
- `confirmed_loss_minor` — подтверждённая величина финансового ущерба;
- `confirmed_loss_currency` — валюта подтверждённого ущерба.

В предлагаемом дизайне:

`confirmed_loss_minor = None`
`confirmed_loss_currency = None`

Значения `None` намеренно обозначают, что по имеющимся данным реальный ущерб не установлен.

**Статус: только проект интерфейса. Модуль ещё не реализован и не тестировался.**

Предлагаемая функциональность не должна изменять логику `score.py` или раскрывать приватные поля разметки через публичный интерфейс агента.

До текущего воспроизведения в репозитории уже существовали генератор сценариев, публичный анализатор, автоматические тесты и документация по другим направлениям LedgerGym.

В рамках общей проверки проекта ранее получено:

Шесть пропусков относились к тестам изолированного Docker runner: закреплённый Docker-образ отсутствовал локально.

Ранее существующий `docs/LG014_REPORT.md` содержит результаты командной работы по генерации сценариев, открытым датасетам, baseline-агентам и воспроизводимости.

Эти результаты не приписываются текущему финансовому аудиту и не суммируются с 1500 проверками.

Отдельный `docs/REPOSITORY_AUDIT.md` посвящён контрактам чтения и пагинации, а не массовому пересчёту денежных величин.

## 11. Ограничения аудита

1. **Синтетические данные.** Проверены сценарии генератора LedgerGym, а не реальные бухгалтерские книги компаний.
2. **Общие правила реализации.** Проверочные скрипты и публичный анализатор используют одинаковую предметную модель, поэтому аудит не является полностью независимым.
3. **Ограниченное покрытие seed.** Для каждой конфигурации использованы seed 0–99. Другие комбинации и граничные случаи могут содержать ошибки.
4. **Повторное использование миров.** Несколько проверок применялись к одним и тем же конфигурациям. Число 1500 обозначает проверки, а не независимые наборы данных.
5. **Нет подтверждённого финансового ущерба.** Проверялись суммы аномалий, а не фактические потери денежных средств.
6. **Compound-overlap.** Суммы связанных ошибок нельзя без дополнительной модели агрегировать в единый ущерб.
7. **Не все проверки автоматизированы в репозитории.** Массовые скрипты воспроизведены вручную; отдельный CI-набор и сохранённые логи ещё не подготовлены.
8. **Docker-пропуски.** Шесть тестов изолированного runner не были выполнены в последнем общем прогоне.
9. **Отсутствие внешней экспертизы.** Независимый профессиональный бухгалтерский аудит не проводился.

## 12. Рекомендации

### Приоритет P1 — воспроизводимость

Сохранить проверочные скрипты в репозитории как отдельные автоматические тесты.

Зафиксировать команды запуска, версию Python, диапазоны seed и ожидаемые инварианты.

Добавить машинно-читаемый отчёт с количеством PASS/FAIL и деталями ошибок.

### Приоритет P1 — корректная финансовая интерпретация

Сохранять различие между величиной аномалии и фактическим финансовым ущербом.

Не суммировать значения разных валют без явно заданных правил конвертации.

Учитывать пересечения compound-ошибок при построении финансовых сводок.

### Приоритет P2 — расширение покрытия

Добавить проверки дополнительных seed, нескольких одновременных ошибок, граничных дат, валютных округлений и необычных комбинаций распределения платежей.

### Приоритет P2 — независимая проверка

Разработать отдельные проверочные эталоны, не использующие реализацию `inspect_company()` как источник ожидаемого результата.

При необходимости провести предметную экспертизу бухгалтерских правил.

### Приоритет P3 — Financial Impact API

После согласования интерфейса реализовать `financial_impact.py` с явной обработкой overlap-групп и отсутствующих данных о реальном ущербе.

## 13. Заключение

Финансовый аудит LedgerGym подтвердил выполнение проверенных бухгалтерских, структурных и денежных инвариантов на 700 комбинациях сценария и seed.

**Итог воспроизведения: 1500 PASS, 0 FAIL.**

Проверки охватили все четыре одиночных типа финансовых ошибок, два составных сценария и чистые бухгалтерские миры.

Результаты подтверждают согласованность проверенных синтетических данных и заявленных величин аномалий в рамках реализованной модели.

Они **не подтверждают реальный финансовый ущерб, отсутствие любых возможных ошибок или прохождение независимого профессионального аудита**.

Следующий рекомендуемый этап — сохранить воспроизводимые проверки в репозитории и оформить их автоматический запуск.
