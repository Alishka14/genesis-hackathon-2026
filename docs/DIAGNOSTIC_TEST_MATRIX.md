# LedgerGym — первые тесты для CAB / EQT / FAA

**Статус:** проект тест-векторов; **не исполнялись** и **не являются результатами benchmark**.
**Владельцы:** №2 (синтетические данные), №4 (оценщик), №3 (изоляция), №1 (интеграция).
**Источники:** `docs/DIAGNOSTIC_EXTENSIONS.md` и официальный контракт GENESIS, после подтверждения схем.
**Gate 0:** до подтверждения участия, AI-правил и согласованного SCOPE не создавать конкурсный код.

## А. CAB: causal/invariance проверка

| ID | Тип | Исходный случай | Преобразование | Ожидаемое поведение |
| --- | --- | --- | --- | --- |
| CAB-01 | Causal flip / invoice refs | По утверждённой policy отсутствие распределения платежа — нарушение; все другие документы позволяют однозначно доказать нераспределённую сумму | Добавить *единственную* обязательную ссылку `invoice_refs` на надлежащий invoice, обновив только необходимые связанные записи | На варианте A нарушение доказано; на B агент не должен объявлять это нарушение |
| CAB-02 | Causal flip / FX | В проводке используется курс не из указанной policy FX-date; эталон суммы и допустимое округление известны | Исправить один причинный параметр расчёта FX и необходимые выведенные значения, сохранив финансовые инварианты | Наличие нарушения меняется; и A, и B разрешимы |
| CAB-03 | Invariance / ordering | Любой согласованный эпизод | Перемешать строки `ledger.csv` и записи JSONL при стабильной пагинации | Canonical issue set, matcher и reward oracle не изменяются |
| CAB-04 | Invariance / ID renaming | Любой согласованный эпизод | Переименовать все публичные IDs и все ссылки согласованным биективным отображением | После обратной нормализации IDs оценки совпадают |
| CAB-05 | Leakage | CAB-01/02 | Агент запрашивает все разрешённые tables, record IDs, documents, manifest и info | `pair_id`, private delta, expected status и закрытый truth недоступны |

**Предупреждение:** CAB-01/CAB-02 — шаблоны для проверки. Прежде чем включать их в работающий набор, участник №2 обязан доказать, что в конкретной модели минимальное изменение действительно меняет truth, а не создаёт новую ошибку или законное исключение.

## В. FAA: категории ложных обвинений

| ID | Исходное условие | Ожидаемое |
| --- | --- | --- |
| FAA-01 | Clean episode, ни одной находки | `FP=0`, стандартные и hard-negative счётчики равны 0 |
| FAA-02 | Clean episode, ложная находка однозначно относится к `STANDARD_VALID` | `fp_standard_valid_count=1`, остальные категории 0 |
| FAA-03 | Clean episode, ложная находка относится к `SUSPICIOUS_BUT_VALID` | `fp_hard_negative_count=1`, официальный FP=1 |
| FAA-04 | Ложная находка с выдуманным ID | `fp_unattributed_count=1`, не угадывать принадлежность |
| FAA-05 | Одно реальное нарушение верно выявлено дважды (одинаковые findings) | Одно совпадение TP; повторный finding считается FP и получает категорию `DUPLICATE_FP` |
| FAA-06 | Два и более FP, в т. ч. неоднозначный или дубликат | `sum(fp_*_count)==FP`; каждый FP отнесён ровно к одному первичному типу |
| FAA-07 | Нет размеченных hard-negative opportunities | `hard_negative_case_fpr=null`/N/A, а не 0 |
| FAA-08 | Три ложные находки на *один* valid case | Официальные FP учитывают все неподходящие findings; case-level FPR numerator = 1 случай |

## Г. Приёмочные «неизменяемые» свойства

1. Сгенерированный эпизод разрешим: для каждого truth issue в публичных данных есть хотя бы один полный допустимый allowed evidence set.
2. Метрики CAB/EQT/FAA не являются частью официальной награды и не позволяют агенту получать hidden truth через observation/info/log.
3. Переименование IDs с обновлением ссылок и перестановка порядка записей не меняют Ground Truth семантически.
4. Отчёт со значением `PASS` возможен **только после реального запуска** теста в согласованной среде.
5. Сначала проверяются official P0 contract/data/reward; эти расширения не блокируют конкурсную сдачу, если остались не реализованы.
